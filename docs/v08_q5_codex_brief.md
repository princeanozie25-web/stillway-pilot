Stillway Labs · Q5 execution brief for Fable

Start from v0.8-trap-graded. Build the questioning guard through the real runner on development jobs. Keep the core and bank fixed. Allow roughly half a day for the build. The 400/400 simulation is a feasibility result with an accurate simulated respondent. This experiment measures the added value and cost of one focused question.

1. Build a disposable probe. Run candidate repairs on a generated legal input in separate copies of the project. Keep the original workspace clean. Ask only when two surviving candidates produce different values for the same field on that input. If an existing public specification resolves it, use it and log the source. If probes find no difference, record the search limit. Commit an equivalent candidate only when supported by a sound equivalence rule for this bounded domain. Otherwise retain the existing guard's clean fallback.
2. Implement pause and resume. Log the candidate patches, probe input, both runner outputs, selected field, job ID and workspace hash before the question. Persist the paused state. Verify the answer belongs to that question before resuming. Test crashes, duplicate delivery, missing or invalid answers and exhaustion of the two-question budget on development fixtures. Clear tentative edits before returning control.
3. Use a blind, two-round handoff. Freeze the implementation, checkpoints, probe budget, random seeds, scoring rules and hashes before opening the public set. For each round, seal all pending questions and the trace digest before sending them to Codex via Prince. Send JSONL with exactly these fields: id (public job ID), round (1 or 2), rows (3–5 triples of key, val, qty), field (count, groups, total or first), predictions (two distinct scalar values, one per candidate). Codex returns id, round, field and the intended scalar value. The private respondent computes this from the held-out specification. The answer can differ from both predictions. Preserve that possibility. Resume the saved run once. Send outputs and costs before grades. No labels, class counts or interim scores are needed.
4. Compare on identical jobs. Run the original guarded bank, plain bank, and questioning guard; keep fixed search as the cheap reference. Use all 120 fresh unselected jobs. Attribute each ending to the procedure or fallback core. Record verified repairs, wrong DONE, clean ASK, limits, user questions, probe executions, total operations and wall time. Report machine time and time awaiting a human separately. Count every probe and every failed candidate. Record the cost of generating questions separately from answering them.
5. Make the decision before opening the set. Proposed primary rule: the questioning guard must deliver more verified repairs than the existing guard, with no increase in wrong DONEs, on paired jobs. Report counts and paired uncertainty; flag small differences as inconclusive for generalisation. Report mean questions across all trap jobs, including zeros, and the share needing a second question. Target at most two per trap, zero on ordinary and equivalent cases, and zero edits left behind when asking. Report every miss, the number of traps actually resolved, and wrong answers against the plain bank. The frozen comparison is against the existing guard even if another reference performs better.
6. Close and move on. Deliver a one-command replay, raw sealed traces, grader-ready final workspaces, one successful question and one failure or clean fallback. Start the ordinary Python repository repair harness while waiting for answers. Use plain-language bug reports, freely written patches, repository-disjoint tests and the same tool budgets for small and larger models. Keep Q5 and general coding results separate. A Q5 win with perfect answers establishes an upper bound for this interaction; a human usability claim needs a separate test with people.

The final cases are committed by hash in the accompanying receipt. Ask Prince for the public input after supplying the freeze identifier. The old 137 cases are spent.
